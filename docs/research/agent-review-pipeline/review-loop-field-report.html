The Review Loop

The greatest review pipeline is not the one with the most reviewers.

It is the one that fixes the review target, demands proof, separates judgment from repair, and knows when to stop.

Executive finding

Keep one review skill. Build one review system.

Do not add a security reviewer, type reviewer, simplicity reviewer, performance reviewer, and testing reviewer as five always-loaded skills. Keep Thermonuclear as the sole dedicated review skill for now. Make its lenses sharper, make the loop outside it explicit, and move objective rules into code.

The design rule The reviewer judges. The controller converges. Scripts prove. AGENTS.md orients.

Reviewer

Reads an exact diff, spec, repo rules, and raw proof. Returns evidence-backed findings. It stays read-only and does not decide how many repair rounds to run.

Controller

Freezes the checkpoint, chooses review lenses, owns finding IDs, assigns one repair owner, enforces the pass limit, and records the terminal outcome.

Proof

Tests, linters, type checks, screenshots, traces, replay seeds, and focused scripts produce facts. Repeated objective comments should become executable checks.

Repository guidance

AGENTS.md holds stable product facts, safety rules, ownership, architecture, and the short review doctrine. Procedures and niche checklists stay behind skills or references.

Why this beats more skills

  • Every loaded description spends discovery context before the agent does any work.
  • Overlapping reviewers create duplicate findings and make severity hard to compare.
  • Fresh review helps; recursive delegation and repeated fresh prompts do not guarantee truth.
  • A named skill is useful only when it owns a distinct trigger, procedure, and checkable result.
  • The strongest workflows use few durable roles, small work units, and hard feedback surfaces.
Controller contract

A loop with brakes

The unit of review is one accepted behavior or structural move. The same base, head, spec, and finding IDs survive the repair pass. The loop ends because the state machine says so, not because a model finally sounds satisfied.

01

Select one accepted unit

Choose one behavior, migration, or structural move with a written finish line.

02

Freeze the target

Resolve and record base, head, task or spec, repository rules, and permitted scope.

03

Run the baseline

Capture the smallest relevant checks before mutation. A pre-existing failure is not a regression.

04

Implement one unit

Keep one mutable owner. Separate behavioral work from structural cleanup where possible.

05

Emit a raw proof packet

Include commands, full outputs, changed tests, direct demonstrations, and known gaps.

06

Review in fresh context

The reviewer sees the contract and evidence, not the implementer’s sales pitch or chain of thought.

07

Verify and deduplicate

Treat each model finding as a hypothesis. Check its location, reachability, and claimed effect.

08

Accept or assign one repair owner

Give the repair owner the whole verified set. Reviewers remain read-only.

09

Rerun proof

Repeat the affected gates and prove the repair did not erase the original behavior.

10

Recheck the same IDs

Score known findings as resolved, partial, unresolved, or invalid. Do not begin a new defect hunt.

Accepted Rejected Blocked Repair budget exhausted

Default repair policy

One repair pass should be the default. A second pass needs prior authorization for high-risk work. Persist the limit before review starts. If material findings remain at the limit, stop and surface the evidence. Never let “run it again” become an unbounded quality policy.

“The technique is deterministically bad in an undeterministic world.”

Geoffrey Huntley on Ralph — source

Ralph’s strongest lesson is not endless autonomy. It is one item per loop, fresh working context, external state, and deterministic feedback. The missing production pieces are independent review, explicit acceptance, and a stop state.

Skill design

Thermonuclear 2.0

Keep the name and the severity. Cut the ritual. The skill should be a compact review contract of about 500–700 words, with optional references for conditional lenses. Its result is a set of checkable findings, not a repair plan pretending to be a verdict.

What the core skill owns

  • Validate an exact non-empty diff and identify the governing task or spec.
  • Read repo rules before applying generic taste.
  • Judge correctness before simplification.
  • Look for invariant breaks, missing behavior, unreachable proof, and tests that cannot fail.
  • Look for removable concepts, branches, policy owners, and caller knowledge.
  • Return only findings with an exact location, failure or cost, smallest repair, and proof method.
  • Say when evidence is missing. Do not fill the gap with confidence.

What leaves the skill

  • Repair ownership, pass counts, rerun policy, CI state, and terminal decisions belong to Dirtyloops.
  • Line-count, forbidden-pattern, generated-file, schema, and dependency rules belong in scripts.
  • Product-specific surface matrices belong in AGENTS.md or a focused repo reference.
  • Security, performance, concurrency, migration, and accessibility become conditional lenses.
  • Generic reviewer personas and motivational prose leave entirely.

The finding record

id
Stable across the initial review and verdict pass.
lens
Correctness, spec, proof, simplification, or a named conditional lens.
severity
Blocker, material, or note. Style-only nits do not block.
confidence
High, medium, or low; never a substitute for evidence.
location
Exact file and smallest useful line range.
fact
The broken invariant or concrete structural fact.
evidence
Source line, test output, counterexample, trace, or reproducible command.
impact
The reachable failure or maintenance cost.
repair
The smallest change that restores the invariant or removes the cost.
proof
The check that should pass after repair.
status
Open, resolved, partial, invalid, accepted risk, or deferred.

The 1,000-line rule becomes a tripwire

The current skill treats crossing 1,000 lines as near-dispositive. Size is useful evidence, but it is not a design verdict. A 1,050-line parser can be one coherent module; a 250-line component can own four policies. Keep the threshold as a prompt to inspect cohesion, change coupling, and ownership. Block only on the actual structural problem.

“Same context reviewing itself isn’t review.”

A reader quoted in Matt Pocock’s review guide — source
Mandatory lens

Correctness needs a kernel

“Looks right” is not a proof strategy. Every material review should ask the same five questions, then add domain checks only when the change earns them.

invariant → reachability → oracle sensitivity → replay → minimized counterexample
Question What it means Useful proof
Invariant What must remain true before, during, and after the change? Types, schemas, assertions, state-machine rules, transaction boundaries.
Reachability Can a real input, event order, or client path reach the claimed failure? A direct call, UI path, event trace, or minimal input sequence.
Oracle sensitivity Would the test fail if the implementation were wrong in the way we fear? Mutation, deliberate breakage, negative case, or differential output.
Replay Can another reviewer reproduce the same result without hidden state? Exact command, seed, fixture, environment, and raw output.
Minimization What is the smallest case that still fails? Shrunk property case, reduced event sequence, or narrow regression test.

High-value techniques, not new skills

  • Property tests for stable invariants across broad input space.
  • Metamorphic tests when no cheap expected-output oracle exists.
  • Differential tests against an old implementation or trusted reference.
  • Bounded fuzzing with recorded seeds and minimized failures.
  • “Parse, don’t validate” at boundaries so invalid states cannot enter the trusted core.

These are techniques the reviewer can request and scripts can execute. They do not need five permanent skill entries. A new skill becomes justified only if a recurring domain procedure has its own trigger and a result the core reviewer cannot express.

“Your job is to deliver code you have proven to work.”

Simon Willison — source
Mandatory lens

Measure ideas removed

Line count is a weak proxy. The stronger question is whether the change makes fewer concepts necessary for the next reader, caller, test, and change.

A practical simplification ledger

Count Look for Review question
Concepts Modes, wrappers, intermediate states, protocols, flags. Can the behavior exist without naming or storing this concept?
Branches Condition chains, scattered special cases, fallback ladders. Can a type, table, boundary, or state transition make the branch disappear?
Policy owners Two modules deciding the same retry, auth, routing, or lifecycle rule. Where is the one place this decision should live?
Caller knowledge Ordering rules, paired calls, magic values, cleanup duties. What can the module absorb so callers know less?
Change surfaces Files and layers touched by one domain change. Does the structure localize the next likely change?

The order matters

  1. Prove the current behavior and name its invariants.
  2. Inline or expose the tangled behavior until its real differences are visible.
  3. Remove dead cases and accidental policy.
  4. Re-extract only the concepts that remain stable and coherent.
  5. Run the same behavior proof again.

This prevents “cleaner” code from quietly changing behavior and prevents a wrong abstraction from gaining more flags. It also gives Thermonuclear a better standard than “split the file.” Sometimes the right move is a deeper module. Sometimes it is honest duplication until the domain becomes clear.

“Duplication is far cheaper than the wrong abstraction.”

Sandi Metz — source
Research synthesis

What the field is teaching

Social posts were useful discovery points. The conclusions below lean on the linked guides, repositories, talks, and primary engineering notes because those show the full procedure and its tradeoffs.

Matt Pocock

Fix the diff base. Keep “built right” and “right thing” as separate axes. Cite repo rules or spec lines. Use fresh context. Treat model findings as hypotheses. Do not recursively run review until it invents a clean result; his guide documents both 50-plus-agent fan-out and non-converging reruns.

Review guide · Executable playgrounds · Deriving vs decoupling

Geoffrey Huntley / Ralph

One item per loop, fresh context, external plans, and tests as backpressure are powerful. The bare Bash loop has no independent acceptance authority and no safe stop rule. Its prompt can also grow into a wall of “signs,” which is the same failure mode as an overgrown AGENTS.md.

Ralph from first principles · Loom prompt

Peter Steinberger

Prefer direct tools and exact review packets. Add agents only when isolation pays for their context and coordination cost. The later removal of a large autoreview/orchestration layer is useful evidence: deleting workflow machinery can improve the workflow.

AI development workflow · Autoreview history

Thorsten Ball / Amp

Separate the author from the reviewer. Give review an exact diff. Use feedback surfaces the agent can read. Amp’s own writing also warns that specialized subagent types can be unclear or unused and shows a bias toward removing handoff machinery when it stops earning its keep.

Agentic review · Feedback-loopable tools · Agents for the agent

Steve Yegge / Gas Town

Durable state, separate roles, and risk-tiered review are worth keeping. Large agent organizations can demand too much human attention and fail to converge. Borrow the ledger and role boundaries, not the whole town, for ordinary review work.

Continuous Thunderdome · Gas Town manual · Review formula

Simon Willison

Start from proof: baseline, direct demonstration, automated regression check, and human accountability. Prefer short repository guidance and command-line tools the agent can drive. Use fresh review when the consequence warrants it, not as a default swarm.

Code proven to work · Designing agentic loops · Subagents

Boris Cherny / Anthropic

Give agents executable definitions of done, preserve state between bounded work sessions, separate builder and reviewer context, verify and deduplicate findings, and start with the simplest workflow. Add autonomy only when the task and evaluator are clear.

Building effective agents · Long-running harnesses · Code review

Addy Osmani

A useful loop has a goal, a strong evaluator, and a stopping condition. Match review depth to risk. Inspect test changes as closely as product code. Demand measurement for performance claims. Treat the third unchanged retry as a stall signal, not a reason for more optimism.

Practical loop engineering · Agentic code review · Agent skills

Mitchell Hashimoto

Small, scoped instruction files and fast objective checks outperform a giant universal prompt. Separate planning from execution when uncertainty is high. Keep human responsibility for semantic acceptance.

AI adoption journey · A scoped AGENTS.md

Kent Beck

Keep a finite acceptance list, take one item, restore green, and separate behavioral changes from structural changes. A review loop should stop when it repeats, weakens the test, or changes the target.

Canon TDD · Thinking about code review · Compact agent guidance

Sandi Metz

Wrong abstractions reveal themselves through accumulating parameters and conditionals. Inline the abstraction, expose the real differences, prune what is no longer needed, then extract again only if a coherent concept remains. Review for the cost of change, not a fixed line target.

The Wrong Abstraction · All the Little Things

Formal testing practice

Hillel Wayne, Alexis King, and matklad point toward invariant-based tests, metamorphic relations, trusted boundary types, replayable fuzzing, and minimized examples. These give a correctness reviewer sharper tools without creating another standing reviewer persona.

Gergely Orosz / review research

Small, self-contained diffs reduce reviewer load. Risk should determine review depth. Repeated objective comments belong in automation. Google and Microsoft review research supports fast feedback, clear rationale, and one accountable reviewer over a crowd of loosely responsible reviewers.

Context architecture

AGENTS.md is a map, not the whole library

The current instruction set contains strong product and safety guidance, but it is close enough to the default project-document ceiling that every repeated block and static inventory has a real discovery cost.

7,901 bytes in the global AGENTS.md
16,753 bytes in Dirtycode’s AGENTS.md
24,654 combined bytes before nested guidance

Codex stops adding project instruction files at 32 KiB by default. Its initial skill list uses at most 2% of the context window, or 8,000 characters when the window is unknown, and may shorten or omit descriptions when the catalog grows. That makes concise routing part of correctness, not merely style.

Keep in AGENTS.md

  • Stable product truth and vocabulary.
  • Safety rules that must apply before any specialized skill loads.
  • Module and ownership boundaries.
  • The shortest working commands and proof expectations.
  • A brief review doctrine: exact target, independent judgment, raw evidence, bounded repair.

Move behind a pointer

  • Long dev-server, pairing, fixture, simulator, and test-data procedures.
  • PR babysitting, deployment, and operational runbooks.
  • Conditional review lenses and domain-specific checklists.
  • Static server or container inventories that drift.
  • Long personal context that can become a short communication contract.

Remove or consolidate now

  • The repo file currently contains two generated Beads Issue Tracker sections.
  • Dirtyloops says helpers are “strongly encouraged” and requires a rationale for using none. Make zero helpers the normal case; delegate only named, independent evidence questions.
  • Thermonuclear is 12,437 bytes while the Dirtyloops review controller is only 2,412 bytes. The judgment contract can shrink; the controller contract should become more exact.

The admission test for any new skill

  1. Does it have a distinct trigger?
  2. Does it encode a recurring procedure, not taste or a persona?
  3. Can it be a conditional lens or reference inside an existing skill?
  4. Can a script, test, linter, or type checker do it more reliably?
  5. Does it return a distinct, checkable artifact?
  6. Does an evaluation show better recall, precision, cost, or review time?
  7. If deleted, what proven capability disappears?

If the answers are weak, do not install it. A small optional reference file is often enough. The research did not find a case for a permanent “correctness critic,” “simplicity critic,” or “test critic” beside Thermonuclear.

Action sequence

Change less, in the right places

Do now

Rewrite Thermonuclear as a read-only review contract. Add correctness, spec, proof, and simplification as its four mandatory lenses. Adopt the shared finding record. Turn the 1,000-line rule into a cohesion tripwire. Remove repair and loop policy from the skill.

Do next

Strengthen Dirtyloops as the sole controller: exact checkpoint identity, one review set, verified and deduplicated findings, one repair owner, one default repair pass, same-ID verdict, and explicit terminal outcomes. Make zero helpers normal.

Then

Trim AGENTS.md. Keep product invariants, the three local hazards, ownership, multi-surface coverage, and targeted verification. Collapse duplicate Beads guidance. Route long operating procedures to the skills that already own them.

Automate

Mine review history. When the same objective comment recurs three or four times, encode it as a focused check. Keep judgment in review only where context changes the answer.

Defer

Do not add new review skills until an evaluation shows a repeated miss that cannot be fixed by the core contract, a conditional reference, or deterministic tooling.

Conditional lenses

Load these only when the diff earns them: security for trust-boundary or secret changes; concurrency and recovery for durable state or async work; migration checks for schema and data changes; performance only with measurement; accessibility for user-facing interaction; T3’s surface matrix for provider, client, contract, reverse-state, and connection-mode changes.

Evidence before rollout

Review the reviewer

The pipeline should earn its place on a fixed evaluation set. Use real past changes with known defects, known false positives, clean diffs, and difficult structural tradeoffs.

Metric Question Bad signal
Known-defect recall How many seeded or historical material defects did it find? More reviewers but no recall gain.
Valid finding rate How many findings survive source verification? Large persuasive reports with weak locations.
False blocker rate How often does style or taste stop a correct change? Generic rules override repo intent.
Duplicate rate How much reviewer output repeats the same failure path? Several agents produce the illusion of consensus.
Repair regressions How often does fixing review feedback break accepted behavior? Reviewer repairs without rerunning original proof.
Convergence Does the same finding set close within the allowed pass budget? Every rerun opens a new review universe.
Cost What tokens, wall time, and human minutes buy one valid material finding? A skill wins aesthetically but loses operationally.

Recommended experiment

Compare the current Thermonuclear plus Dirtyloops flow against the compact contract on 20–30 closed changes. Keep the model, diff, spec, and proof packet fixed. Have a human label findings blind. Adopt the rewrite only if it matches or improves material recall while reducing invalid findings, duplicate output, and review cost.

Scope notes

What this report did not claim
This is not a statistical survey of developer practice and does not treat follower count as evidence. It is a pattern synthesis from public practitioner artifacts, formal testing guidance, review research, official agent documentation, and the current local skill and instruction files.
Design assumption
The user fixed the visual direction: white text on true black. This artifact treats that as a complete editorial constraint, stays self-contained, uses no remote assets, and favors reading over interaction.
Decision boundary
The report recommends changes but does not modify Thermonuclear, Dirtyloops, AGENTS.md, or any runtime policy. Those changes need their own accepted task and evaluation run.
