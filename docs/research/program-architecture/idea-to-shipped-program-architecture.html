From idea to shipped.

An independent review of graphs, loops, Beads, and T3 Code—and a concrete path from today’s fragile orchestration to a workflow that can earn the right to act.

Recommendation

Build a T3-native Program system. Let plans change while the problem is unclear. Once accepted, run a typed, immutable work graph whose authority and evidence T3 owns.

01 / Verdict

Make Program a native T3 concept.

The strongest answer is neither “graphs replace loops” nor “keep Beads at the center.” It is a two-mode system with a clean authority boundary.

Before acceptance, research and planning stay adaptive. People and agents can question the shape of the feature, run prototypes, revise the spec, and reorder work without pretending that an early guess is law. Acceptance creates an immutable ProgramRevision: typed work nodes, dependency edges, evidence rules, and grants that say what may act. The present dirtycode Program contract is the starting point for that redesign [12].

After acceptance, a pure ProgramKernel decides the next legal actions from durable facts. T3 provides the effect outbox, worker attempts, retained results, thread history, Git identity, receipts, and recovery. External tools can report facts or show a projection. They do not own the Program.

Adaptive authoring

Wayfinding, questions, prototypes, product decisions, and semantic plan review. No mutation authority yet.

Accepted revision

An immutable, content-addressed work graph. It records scope, dependencies, evidence policy, and explicit grants.

Program kernel

A pure decision function: facts in, next legal commands out. It performs no network, shell, tracker, or Git I/O.

T3 execution

Durable events, effect attempts, worktrees, threads, retained results [11], receipts, recovery, and multi-client projections.

Optional adapters

Beads, Git documents, issue trackers, and bounded agent workflows import or project state. None becomes canonical by accident.

Supersedes an earlier finding

dirtyloops is slowly becoming a workflow inside dirtycode, and dirtycode is fixed on T3. That product choice changes the architecture. A separate durable dirtyloops runtime would now duplicate T3’s strongest primitives and create two owners for one run.

02 / Committee

A close result, not a vague consensus.

Four independent judges received the same evidence packet and did not confer. Three chose the native accepted graph. One chose the adaptive journal.

The three-point gap matters. The graph won on auditability, dependency semantics, and safe replanning. The journal nearly won on simplicity and migration cost. The right reading is a hybrid: use the journal-like adaptive mode to discover the work, then accept a graph before the system gains authority to mutate code or external state.

Project evidence The vote, rubric, and scores came from the independent committee run for this architecture review. They are not a public benchmark or a vendor claim.

What the score does—and does not—mean

These figures are project research, not an external benchmark. The committee scored architectural fit for dirtycode under the stated constraints: safety, recovery, inspectability, user experience, migration cost, tracker independence, and fit with T3. A changed constraint can change the result.

03 / Model

A graph describes. A loop decides.

Graphs and loops solve different problems. Treating them as rivals hides the useful design.

The graph

Records the accepted work, prerequisites, evidence, and provenance. It answers: “What must be true, and what depends on what?”

The loop

Chooses tactics as new facts arrive. It answers: “Given what we know now, what legal action should happen next?”

Do not force every relationship into one universal graph. This system contains at least seven: the plan DAG, node lifecycle transitions, thread lineage, evidence provenance, Git ancestry, recovery lineage, and the live execution tree. They can share identifiers without sharing one data model.

That distinction also protects the product from a “dirtygraphs” detour. A graph database is not needed. Typed relational records, append-only events, and precise queries cover the first useful version.

Plain-language test

If an edge changes what work is allowed, it belongs in the accepted Program. If it only helps a tracker display or organize work, it is a projection.

04 / Workflow

Preserve the strongest part of the Matt Pocock flow.

The suggested workflow is strong because it separates discovery from implementation and keeps each agent context bounded. Keep that. Change where durable authority lives.

Use wayfinding for unresolved work, focused prototypes for risky questions, an approved spec, tracer-bullet slices, fresh implementation contexts, fixed-range reviews, and one durable goal per settled phase. This keeps deterministic workflow steps separate from the places where an agent’s judgment is useful [5]. But do not let a tracker issue or IMPLEMENT.md become runtime truth. Acceptance should compile or snapshot that plan into the native Program. This assessment refers to the private suggestion packet supplied for this review; readers cannot inspect that packet from this public page.

For a small feature

Start one T3 task. State the outcome, constraints, acceptance checks, and authority. T3 creates a one-node Program, runs implementation in a worktree, requests a fixed review, runs CI against the exact commit, then integrates with compare-and-swap protection.

For a large feature

  1. Research without mutation authority.Question, grill, compare, and build throwaway prototypes.
  2. Record decisions and non-goals.Make product boundaries clear before producing tickets.
  3. Draft the spec and tracer graph.Use vertical slices that each produce testable user value.
  4. Review the plan’s meaning.Challenge missing work, false dependencies, weak checks, and hidden authority.
  5. Accept revision R1.Content-address the nodes, edges, evidence rules, and grants.
  6. Schedule through T3.Give each bounded node a fresh task, attempt, and worktree identity.
  7. Prove each gate separately.Implementation, review, CI, integration, and release are distinct facts.
  8. Propose R2 when reality changes.Show a semantic diff and require acceptance before new authority exists.
  9. Carry work forward carefully.Reuse results only when inputs, dependencies, and evidence policy still match.
  10. Keep publish and deploy explicit.A completed build does not silently grant release authority.

Goals

A goal supplies liveness: it keeps the system working toward an outcome. It does not prove completion, grant authority, or replace a receipt.

05 / Authority

Make the owner visible at every stage.

Most orchestration failures are not scheduling failures. They are authority failures: two writers act, a stale worker reports success, or a useful tool quietly becomes the source of truth.

Where each current tool belongs

  • T3 owns Program identity, revisions, the event journal, effect attempts, retained results, receipts, threads, worktrees, and recovery.
  • dirtyloops supplies plan compilation, scheduling and recovery policy, review and CI rules, conformance tests, and optional adapters.
  • Beads can supply repo task tracking, dependencies, team memory, CLI access, and an import or projection.
  • Git supplies immutable code identity and compare-and-swap integration—not a mandatory write path for starting a local Program.

06 / Present fault

The current branch has a custody defect.

A valid slow result can arrive after the scheduler’s right to settle it has expired.

On the inspected dirtycode source revision, the Program wake lease lasts 30 seconds [7]. A callback can wait 120 seconds [8]. The dirtyloops driver can reconcile for 30 minutes [9]. After the effect returns, settlement checks the original lease again [10]. This couples a short scheduling lease to a long external action.

scheduler obtains 30 s lease → callback waits up to 120 s → driver may reconcile for 30 min → valid result returns → settlement rechecks expired scheduler lease → result cannot be safely accepted

Required correction

Decide and enqueue inside a short transaction. Give the long operation its own effect and attempt identity. Return its result as a durable observation. Settle by effect and attempt ID—not by the scheduler lease that chose the work. If a crash leaves an external outcome unknowable, stop and ask for reconciliation; do not retry blindly.

This is why preserving T3’s guarantees matters more than preserving the current class shapes. Keep ordered events, idempotent requests, the effect outbox, retained attempt results, worktree and commit identity, and restartable projections. Replace blocking callbacks, driver-returned projections, Beads-derived identity, the mandatory coordinator hierarchy, the fixed seven-stage rail, and payload-free replans.

The current experience branch is also the wrong base for more runtime work. Local project inspection—not independently available from this public page—found 8 commits, 8,434 added lines, and 145 files above its fork point, with nearly all changes in plans, generated artifacts, hooks, and Beads state rather than product code. Treat it as a design record, not the trunk for Program v2.

Beads is useful, not foundational

Beads 1.1 has real strengths: formulas, molecules, gates, Dolt-backed history, a server mode, and federation work [2]. Yet local project inspection found that the current dirtyloops integration only consumes a small subset—epics, children, and blocking links—and bypasses most of that machinery. More important, a tracker does not know whether a terminal result is retained, a review covers the exact commit, a Git ref moved, or a release grant exists.

Pi dynamic workflows is a strong local instrument

The inspected project can turn a request into deterministic JavaScript orchestration with parallel agents, pipelines, phases, journaled resume, worktree isolation, model routing, verification, judge panels, dry-loop review, and completeness checks [1]. That is valuable inside a bounded Program node. It should report an outcome and evidence back to T3, not become the Program ledger.

08 / Migration

Stop stacking on the experience branch.

Build Program v2 on a curated T3 integration base, behind one narrow capability seam.

verified upstream T3 ↓ curated T3 integration branch ↓ Program v2 kernel branch ↓ Program UX and optional adapters

The integration branch should contain only the unmerged T3 features Program actually needs. Expose threads, attempts, effects, observations, Git identity, and client changes through a narrow Program capability interface. Run the same conformance suite against the curated base and the latest upstream T3 on a regular cadence.

Do not delete applied database migrations. Add a forward migration for the new revision and receipt model. Keep legacy tables readable for import and rollback until Program v2 has proved replay, recovery, and UI parity.

This approach acknowledges reality: T3 has useful unmerged primitives, but the current dirtycode Program shell is also fork-only. It avoids pretending that either the upstream base or today’s large feature branch is already stable.

09 / Build order

Prove custody before building the cockpit.

  1. Write the fault harness.Reproduce expired leases, duplicate results, crashes, and ambiguous effects before changing the architecture.
  2. Define immutable Program revisions.Add typed nodes, edges, evidence rules, grants, and content digests.
  3. Build the pure Program kernel.Facts in; legal decisions out. No I/O and deterministic replay.
  4. Move slow work behind the T3 outbox.Use retained attempt observations and separate effect leases.
  5. Ship one tracker-free tracer.Implement, review, CI, and compare-and-swap integration on an exact commit.
  6. Implement real replanning.Create R2 with a semantic diff and explicit carry-forward rules.
  7. Build the Program UI.Show revision, authority, facts, pending effects, evidence, and recovery state.
  8. Add optional adapters.Import from or project to Beads and Git documents after the native path works.
  9. Run the upstream rebase trial.Measure which seams survive and narrow any that leak fork details.

First usable slice

A user accepts a three-node Program—implement, review, integrate—closes the app mid-run, returns later, and sees one correct state with retained evidence. No Beads repository exists. No callback process has to stay alive.

10 / Kill tests

Try to break the claims that matter.

Green unit tests are not the bar. The system should survive the exact failures that make autonomous work untrustworthy.

  • A slow result arrives after several scheduler lease periods; the system records one action and one receipt.
  • The process crashes before the external action, after the action, and before its receipt.
  • Results are lost, duplicated, reversed, delayed, or conflict with a prior observation.
  • A provider remains live but silent; the Program distinguishes waiting from lost custody.
  • R2 changes one node; unchanged work carries forward only when its inputs, dependencies, and evidence policy match.
  • The repository has no bd command and no .beads directory.
  • Review and CI bind to the exact commit; integration fails safely when the target ref moves.
  • A build completes without a release grant; nothing publishes or deploys.
  • Full replay yields the same projection and the same set of pending effects.
  • The Program seam survives a rebase onto the latest upstream T3.

11 / Incident

The hung Lavender tasks exposed a different seam.

The remote task failure was not proof that Program graphs are wrong. It was a control-plane and single-writer failure.

Local process and task evidence—not publicly reproducible from this page—showed that the original task started under Codex 0.149.0 while its app server reported 0.149.1. The installed CLI then changed to 0.150.1 without a server restart, and the old process referred to a deleted package executable. The task resumed without a clear new UI projection and appeared to reuse event positions. A recovery task then became a second writer in the same checkout and on the same Beads issue.

The safe operational answer is to leave both old tasks idle, restart the Lavender di remote connection, verify the running and installed versions agree, then create one fresh bounded writer. OpenAI’s remote connection guide provides the public operating context [6]. The product lesson is larger: T3 must make writer custody, runtime version, lease owner, last durable event, and retained terminal result visible. A recovery action must transfer custody, not merely start another agent.

Do not conflate

The remote incident and the Program wake-lease defect can produce similar symptoms—an apparently hung task—but they have different causes and need separate fault tests.
